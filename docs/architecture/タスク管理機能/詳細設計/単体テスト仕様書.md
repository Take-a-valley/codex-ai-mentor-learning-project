# 単体テスト仕様書

## 1. 目的・管理方針

本書は単体テストの具体的な条件・入力・手順・期待結果・実施状況を管理する正本とする。テスト全体の方針と他種別の観点は[テストケース設計書](テストケース設計書.md)および[テスト方針書](../基本設計/テスト方針書.md)を参照する。

管理形式はUTF-8のMarkdownとする。テキストとして読み書き・検索・Git差分レビューができ、GitHub上の閲覧やQiita記事への抜粋に利用しやすいためである。Excel版との二重管理は行わない。将来Excelへ出力する場合も本書を正本とする。

機密情報・実在ユーザーの個人情報を記載しない。テストデータには架空の値を使い、パスワードハッシュ等の内部値を公開用の期待レスポンスに含めない。

## 2. 実施タイミングと範囲

単体テストへ移行する際、AIは関連設計・本書・対象実装を確認し、ケース記載が不足していれば、ユーザーからの継続的な編集許可に基づき関連する設計書Markdownへ自動追記する。入力・手順・期待結果・検証範囲・実施状態を実装前に明示し、結果の正本は本書に集約する。未確定の仕様・期待値は推測せず確認する。この許可はソース・設定の編集やGit変更操作を含まない。

意味のある処理の実装・レビュー直後に単体テストを作成・実行する。Controllerや機能全体の完成を待たない。関連部品の実接続後には結合テストを別途行う。

対象はUserService、MasterDataService、LoginRequestの入力検証、LoginUserDetails。ServiceテストではRepositoryをMockitoで置き換え、JUnit Jupiterで結果を検証する。LoginRequestはJakarta ValidationのValidatorを直接使用する。LoginUserDetailsは実物を生成して戻り値を検証する。後者2つではMockitoやSpringのアプリケーション起動を必要としない。実DB・Docker・ログインは本書の単体テストの前提としない。

モックの空結果による例外確認は、実DBの論理削除条件の検証ではない。固定マスタの順序確認はRepositoryから受け取った順序を維持することの検証であり、SQLのORDER BYの検証ではない。HTTPステータス・JSON・認証は別のテスト範囲とする。

### 4.7 LoginRequest入力検証（UT-AUTH-DTO-001〜008）

根拠はDTO設計書8.1のemail必須・メール形式・password必須と、現在のLoginRequestに定義したNotBlank・Email制約とする。既存のService6ケースとは別の追加ケースであり、過去の6件成功ログは本ケース群の成功証跡にはしない。

#### 共通準備・手順

1. Jakarta Validationの既定プロバイダーからValidatorFactoryを生成し、Validatorを取得する。
2. 次表の入力を持つLoginRequestを作成する。項目の同時不正は今回対象とせず、不正にする項目以外は正常値にする。
3. Validator.validateで制約違反の集合を取得する。recordの生成だけでは検証を実行したことにならない。
4. 正常系は違反集合が空であることを確認する。異常系はプロパティパスと制約の型の組み合わせを確認する。
5. ValidatorFactoryはテスト終了時にcloseする。テストごとに生成する場合も、クラス単位で共有する場合も、終了処理で確実に解放する。

各正常値・パスワードは架空のテストデータで、実アカウントには使用しない。DTO全体・パスワードをログやアサーションメッセージへ不用意に出力しない。

#### 検証の判定方法

- UT-AUTH-DTO-001：制約違反が0件であること。認証成功やDB登録済みを意味しない。
- UT-AUTH-DTO-002〜004：emailのNotBlank違反を含み、正常なpasswordに違反がないこと。
- UT-AUTH-DTO-005：emailのEmail違反を含み、emailのNotBlank違反と正常なpasswordの違反がないこと。
- UT-AUTH-DTO-006〜008：passwordのNotBlank違反を含み、正常なemailに違反がないこと。
- 制約型はConstraintViolationのConstraintDescriptorから取得するアノテーションの型で判定する。違反の列挙順やプロバイダーの既定メッセージには依存しない。
- emailの空文字・空白等では、EmailとNotBlankの違反が重なる場合がある。異常系で一律に違反総数1件を要求せず、上記の項目・制約を確認する。
- JSON本文の欠落・不正、バリデーション結果のHTTP変換、CSRF・セッション、パスワード照合、パスワード強度・最大長の追加仕様は本ケース群の対象外。

### 4.9 GlobalExceptionHandler（UT-EXCEPTION-001）

- 根拠：例外設計書4章の共通エラー形式、404 / RESOURCE_NOT_FOUNDの契約、GlobalExceptionHandler.handleResourceNotFoundの既存実装。
- 準備：GlobalExceptionHandlerの実物と、メッセージ「ユーザーが見つかりません。」を持つResourceNotFoundExceptionの実物を生成する。Mockito・DB・Spring Boot起動は不要。
- 手順：呼び出し直前にOffsetDateTimeで時刻を記録し、handleResourceNotFoundを直接1回呼び出し、直後の時刻を記録する。
- 期待結果：ResponseEntityがnullではなく、ステータスが404である。本文がnullではなく、codeがRESOURCE_NOT_FOUND、messageが指定した例外メッセージと完全一致する。detailsはnullではなく空、timestampはnullではない。
- 日時検証：timestampが呼び出し前の時刻以降かつ呼び出し後の時刻以前であることを確認する。境界の同時刻を許容し、固定日時との一致や日本時間のオフセットを要求しない。OffsetDateTimeのisBefore/isAfter等で時点を比較し、sleepは使わない。実行中にシステム時計が補正される場合は範囲検証が不安定になり得るため、再発時はClock導入を別途検討する。
- 1ケース1テストとし、本文の項目参照前に非nullを確認する。これは既知の例外を応答へ変換する処理の検証であり、テスト自体の成功条件は例外を投げることではない。
- 対象外：RestControllerAdvice / ExceptionHandlerによる自動捕捉、HTTP通信、JSONシリアライズ、他例外・Securityフィルターの401/403。後続のMVC・接続テストで別途確認する。未実装のハンドラを本ケースの対象へ追加しない。
- 実行：mvn -f backend/pom.xml "-Dtest=GlobalExceptionHandlerTest" test。単独1件の成功報告は5.6、mvn -f backend/pom.xml testによる全18件成功の報告は5.7参照。

### 4.11 PasswordEncoder設定（UT-AUTH-PASSWORD-001〜003）

- 根拠：セキュリティ設計書16.1。SecurityConfig.passwordEncoderが返す実物をテストし、テスト側だけで別のEncoder設定を作らない。設定メソッドと001〜003は実装・レビュー済み、3件成功は5.14参照。

- 003：TestPass123!で生成した保存文字列へ、異なる平文WrongPass456!をmatchesで照合するとfalseになることを確認する。
