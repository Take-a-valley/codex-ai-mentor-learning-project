# 単体テスト仕様書

## 1. 目的・管理方針

本書は単体テストの具体的な条件・入力・手順・期待結果・実施状況を管理する正本とする。テスト全体の方針と他種別の観点は[テストケース設計書](テストケース設計書.md)および[テスト方針書](../基本設計/テスト方針書.md)を参照する。

管理形式はUTF-8のMarkdownとする。テキストとして読み書き・検索・Git差分レビューができ、GitHub上の閲覧やQiita記事への抜粋に利用しやすいためである。Excel版との二重管理は行わない。将来Excelへ出力する場合も本書を正本とする。

機密情報・実在ユーザーの個人情報を記載しない。テストデータには架空の値を使い、パスワードハッシュ等の内部値を公開用の期待レスポンスに含めない。

## 2. 実施タイミングと範囲

意味のある処理の実装・レビュー直後に単体テストを作成・実行する。Controllerや機能全体の完成を待たない。関連部品の実接続後には結合テストを別途行う。

対象はUserService、MasterDataService、LoginRequestの入力検証。ServiceテストではRepositoryをMockitoで置き換え、JUnit Jupiterで結果を検証する。LoginRequestはJakarta ValidationのValidatorを直接使用し、MockitoやSpringのアプリケーション起動を必要としない。実DB・Docker・ログインは本書の単体テストの前提としない。

モックの空結果による例外確認は、実DBの論理削除条件の検証ではない。固定マスタの順序確認はRepositoryから受け取った順序を維持することの検証であり、SQLのORDER BYの検証ではない。HTTPステータス・JSON・認証は別のテスト範囲とする。

### 4.7 LoginRequest入力検証（UT-AUTH-DTO-001〜008）

根拠はDTO設計書8.1のemail必須・メール形式・password必須と、現在のLoginRequestに定義したNotBlank・Email制約とする。既存のService6ケースとは別の追加ケースであり、過去の6件成功ログは本ケース群の成功証跡にはしない。

#### 共通準備・手順

1. Jakarta Validationの既定プロバイダーからValidatorFactoryを生成し、Validatorを取得する。
2. 次表の入力を持つLoginRequestを作成する。項目の同時不正は今回対象とせず、不正にする項目以外は正常値にする。
3. Validator.validateで制約違反の集合を取得する。recordの生成だけでは検証を実行したことにならない。
4. 正常系は違反集合が空であることを確認する。異常系はプロパティパスと制約の型の組み合わせを確認する。
5. ValidatorFactoryはテスト終了時にcloseする。テストごとに生成する場合も、クラス単位で共有する場合も、終了処理で確実に解放する。

各正常値・パスワードは架空のテストデータで、実アカウントには使用しない。DTO全体・パスワードをログやアサーションメッセージへ不用意に出力しない。

| UT-AUTH-DTO-007 | passwordが空文字 | user101@example.com | "" | password / NotBlank |

#### 検証の判定方法

- UT-AUTH-DTO-001：制約違反が0件であること。認証成功やDB登録済みを意味しない。
- UT-AUTH-DTO-002〜004：emailのNotBlank違反を含み、正常なpasswordに違反がないこと。
- UT-AUTH-DTO-005：emailのEmail違反を含み、emailのNotBlank違反と正常なpasswordの違反がないこと。
- UT-AUTH-DTO-006〜008：passwordのNotBlank違反を含み、正常なemailに違反がないこと。
- 制約型はConstraintViolationのConstraintDescriptorから取得するアノテーションの型で判定する。違反の列挙順やプロバイダーの既定メッセージには依存しない。
- emailの空文字・空白等では、EmailとNotBlankの違反が重なる場合がある。異常系で一律に違反総数1件を要求せず、上記の項目・制約を確認する。
- JSON本文の欠落・不正、バリデーション結果のHTTP変換、CSRF・セッション、パスワード照合、パスワード強度・最大長の追加仕様は本ケース群の対象外。
