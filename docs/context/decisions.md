# Decisions

| 日付 | 決定事項 | 判断理由 | 影響範囲 |
|---|---|---|---|
| 2026-10-29 | 共通基盤の整備後、利用者の操作を完結できる機能単位でバックエンド・フロントエンド・必要なテストを実装する | 早期に画面からAPI・DBまで接続し、仕様や認証・通信の不整合を検出するため | 実装順序・タスク提示。各単位でAPI・画面・テスト・完了条件を整理する。単体テストは処理の実装直後、結合テストは接続後とする。従来の層別一括実装順序に優先。設計書本文は未反映 |
| 2026-10-27 | 作業目的ごとのブランチで開発し、実装・レビュー・必要なテスト完了後にmainへマージする。PRは必須としない | 個人開発でも未完成の変更を分離し、実務に近い変更管理を学ぶため | Git運用、実装計画、AI運用。コミット・push・マージはユーザー判断とし、AIは指示なく実行しない |
| 2026-10-23 | UserServiceは内部検索・DTO変換を担当し、本人情報は既存のGET /api/auth/meで返す | 認証・招待・メンバーAPIの責務とレスポンス契約を維持するため | API設計書7.4、Controller設計書7.4〜7.6、Service設計書10章 |
| 2026-10-23 | 一般の対象不在は404、認証上の本人不在・削除済みは401として扱う | 対象検索と認証失敗の意味を区別するため | UserService、AuthService、例外ハンドラ、Security |
| 2026-10-23 | 【2026-10-25に更新済み】当時は機能単位の実装後にテストを追加する方針 | 現在は次行の実装並行方針を適用する | 過去の決定履歴 |
| 2026-10-25 | 意味のある処理の実装・レビュー直後に単体テスト、部品接続後に結合テストを行う | 早期に変換・判断・例外を検証し、後続変更の回帰を確認するため。TDDは必須にしない | テスト方針、実装計画、Service、AI運用 |
| 2026-10-23 | 共通ErrorResponse.timestampはOffsetDateTimeを使用する | 発生日時をUTCとの時差付きで返すため。現実装は環境既定ゾーンのnow()を使用 | ErrorResponse、GlobalExceptionHandler |
| 未記録 | AIは実装代行ではなくメンターとして使う | 学習効果を重視するため | 開発プロセス全体 |
| 未記録 | 設計書は `/docs/architecture/` にユーザー主体で作成する | 設計力を身につけるため | ドキュメント管理 |
| 2026-07-01 | 実装開始前の最終整理では、実装開始に必要な未決事項のみ決める | 実装前にすべてを決め切るより、初期MVP開始に必要な判断へ絞るため | 詳細設計完了後の実装準備 |
| 2026-07-01 | Next.jsはApp Routerを採用する方針 | Next.js 16系ではApp Routerが主流で、今後の標準構成として学びやすいため | フロントエンド構成、ルーティング |
| 2026-07-01 | shadcn/uiは必要箇所のみ使用する方針 | Tailwind CSSを基本にしつつ、フォーム、モーダル、ダイアログ、テーブルなどを効率よく実装するため | フロントエンドUI |
| 2026-07-01 | パスワードルールは8文字以上72文字以下、英字と数字を各1文字以上、記号任意を推奨方針とする | 初期MVPとして実装しやすく、最低限の強度を確保するため | 認証、入力チェック、テスト |
| 2026-07-01 | ログイン失敗回数制限は初期MVP対象外とし、将来拡張とする方針 | アカウントロックや解除設計まで範囲が広がるため | 認証、セキュリティ |
| 2026-07-01 | 招待・パスワードリセットの期限切れ処理は参照時に判定する方針 | バッチ処理を作らず初期MVPとして実装しやすいため | 招待、パスワードリセット |
| 2026-07-01 | JavaのID型はLong、日時はLocalDateTime、期限日はLocalDateを基本方針とする | Spring Boot / JPAで扱いやすく、業務データとして自然なため | Entity、DTO、Repository |
| 2026-07-01 | tokenは推測困難なランダム文字列としてDB保存する方針 | 初期MVPでは学習・実装難度を抑えるため | 招待、パスワードリセット |
| 2026-07-01 | ControllerではSpring Securityの認証情報からログインユーザーを取得し、ServiceへログインユーザーIDまたは情報を渡す方針 | Service層で認可判定しやすくするため | Controller、Service、Security |
| 2026-07-01 | 一般的な開発順序に準じ、環境・DB・バックエンド基盤から実装を開始する方針 | 業務アプリ開発の一般的な流れに沿い、土台を安定させるため | 実装計画 |
| 2026-07-22 | Gitのコミット・プッシュはユーザー指示時に行う | コミット単位はユーザーが作業終了前に判断するため | 作業進行、タスク提示、終了報告 |
| 2026-07-30 | ユーザーの明示指示がある場合、AIは `/docs/architecture/` 配下の設計書Markdownも編集・新規作成できる | 実装中に設計書の不足や変更が判明した場合、設計と実装の整合性を保つため | 設計書運用、レビュー、実装前整理 |
| 2026-07-30 | 固定マスタ取得APIでは `MasterDataResponse` を使用し、ProjectRole、TaskStatus、TaskPriorityをまとめて返却する | MasterDataServiceでEntityを直接返さず、画面初期表示に必要な固定マスタを一括取得できるようにするため | DTO設計、MasterDataService、Controller |
